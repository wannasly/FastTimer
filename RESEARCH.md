# FastTimer · исследование Windows 11

## BetterTimerResolution

Проверен коммит `131a0b1e7a2e86a2457360f5372eda293e068a00`. В дереве находятся README и изображения. Скрипт и EXE из инструкции хранятся за внешней ссылкой. README описывает подбор интервала по близости `Sleep(1)` к 1 мс и стандартному отклонению, прогон на Windows 11 23H2, нагрузку Prime95 и отдельный тест FPS в CS2. [Репозиторий BetterTimerResolution](https://github.com/plankeeee/BetterTimerResolution/tree/131a0b1e7a2e86a2457360f5372eda293e068a00)

Публичный исходник инструментов, на которые ссылается автор методики, проверен отдельно по коммиту `f9eade776b127ecfef3c9325156aea7c1fc2c561`. `MeasureSleep` читает `NtQueryTimerResolution`, а длительность `Sleep(n)` измеряет парой вызовов `QueryPerformanceCounter`. `SetTimerResolution` вызывает `NtSetTimerResolution(TRUE)` и остаётся запущенным. Скрипт перебирает периоды, запускает держатель запроса и измеритель как отдельные процессы, ждёт стабилизации и собирает среднюю дельту и стандартное отклонение. Версия файлов из внешнего архива BetterTimerResolution не подтверждалась. [MeasureSleep.cpp](https://github.com/valleyofdoom/TimerResolution/blob/f9eade776b127ecfef3c9325156aea7c1fc2c561/MeasureSleep/MeasureSleep.cpp), [SetTimerResolution.cpp](https://github.com/valleyofdoom/TimerResolution/blob/f9eade776b127ecfef3c9325156aea7c1fc2c561/SetTimerResolution/SetTimerResolution.cpp), [скрипт сравнения](https://github.com/valleyofdoom/TimerResolution/blob/f9eade776b127ecfef3c9325156aea7c1fc2c561/micro-adjust-benchmark.ps1)

В опубликованных сравнениях `GlobalTimerResolutionRequests` и `disabledynamictick` меняются вместе. Эффекты этих настроек отдельно не измерены. Прогон CS2 на одном ПК не устанавливает причинную связь между периодом и FPS, а `Sleep(1)` не моделирует цепочку от ввода до вывода кадра.

## TimerResolution Лукаса Хейла

Автор описывает первоначальный эффект мультимедийных запросов, которые на старых системах меняли разрешение для всей системы, и переход к Native API. В официальном описании v2 заявлены фоновый режим и CLI. Здесь исследовался бесплатный локальный v1.2. [История автора](https://www.lucashale.com/timerresolution/history/), [официальные версии](https://www.lucashale.com/timerresolution/download/)

- Локальный `TimerResolution-V1.2.zip` побайтно соответствует скачанному архиву автора по SHA‑256 `7bcb16d0c7d421091b04fcd6f9405cc2440eafe0b3cdf9c48f026eec8802a31d`. У вложенного EXE SHA‑256 `8a0c6871ec6e09e4193f537884111006a947d7b3e9260110907777d0c4dd68d3`. [Архив автора](https://lucashale.com/TimerResolution-V1.2.zip)
- `dumpbin /headers /imports` определил PE32/x86, GUI-подсистему, версию 1.2.0.1, MFC42 и импорты `NtQueryTimerResolution` и `NtSetTimerResolution` из `ntdll.dll`. Authenticode-подписи нет. По дизассемблированию видны отдельные вызовы Native API с флагами установки и снятия. Исследование ограничилось диагностикой внешнего поведения и вызовов API. В FastTimer нет кода или бинарных файлов оригинала.
- При запуске оригинал показал границы 15,625 и 0,500 мс и текущие 0,500 мс. После нажатий **Maximum** и **Default** показание осталось 0,500 мс. При включённом **Maximum** медиана `Sleep(1)` отдельного измерителя оставалась 15,573 мс (60 замеров). По одному показанию текущего разрешения нельзя определить эффект на чужой процесс.

## API и пределы применимости

- `NtQueryTimerResolution` возвращает границы и текущий период в 100 нс. Меньший период означает более высокое разрешение. `NtSetTimerResolution` принимает период в тех же единицах и однобайтовый `BOOLEAN`. Возвращаемый интервал и статус системного вызова учитываются отдельно. Это Native API без публичного контракта Win32. [Заголовок System Informer](https://github.com/winsiderss/systeminformer/blob/master/phnt/include/ntexapi.h)
- `timeBeginPeriod` принимает целые миллисекунды, поддерживаемый диапазон доступен через `timeGetDevCaps`. Каждому успешному вызову соответствует `timeEndPeriod` с тем же аргументом. Microsoft документирует переход к запросам в контексте процессов начиная с Windows 10 2004. Для полностью перекрытых, свёрнутых или иначе невидимых и неслышимых окон Windows 11 может игнорировать повышение разрешения. `SetProcessInformation(ProcessPowerThrottling)` позволяет управлять политикой для своего процесса. Эти гарантии WinMM нельзя автоматически переносить на все сборки Native API. [timeBeginPeriod](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod), [SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)
- `QueryPerformanceCounter` измеряет прошедшее время независимо от выбранного периода системного таймера. `Sleep` переводит поток в состояние ожидания, а по истечении ожидания планировщик решает, когда готовый поток снова получит процессор. [QueryPerformanceCounter](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps), [Sleep](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-sleep)

## Контрольный замер FastTimer

Windows 11 25H2 x64, сборка 26200.8457. Параметр `GlobalTimerResolutionRequests` отсутствовал при чтении. Windows сообщала диапазон 0,5000–15,6250 мс и текущий период 0,5000 мс уже до теста. Три прохода, 20 прогревочных и 200 измеряемых ожиданий на режим в каждом проходе. Дополнительная нагрузка не создавалась.

| Режим | Медиана, мс | P95, мс | P99, мс |
|---|---:|---:|---:|
| Без запроса | 15,556 | 16,059 | 16,107 |
| Native, кратчайший (0,5000 мс) | 1,502 | 2,006 | 2,026 |
| Native, 0,5100 мс | 1,502 | 2,010 | 2,033 |
| Native, 1,0000 мс | 1,502 | 2,010 | 2,043 |
| WinMM, 1 мс | 1,501 | 2,010 | 2,046 |

Пока отдельный процесс FastTimer удерживал 0,5000 мс, измеритель без собственного запроса показал медиану 15,560 мс (60 замеров). После снятия запроса Windows по-прежнему сообщала 0,5000 мс. Замер не даёт оснований считать, что разница между 0,5000 и 0,5100 мс улучшит задержку ввода или FPS.

## Проверка выпуска 1.0.0

Повторный прогон на Windows 11 25H2 через `scripts/Test-CrossProcess.ps1 -Samples 60`, по 180 измерений на режим. Видимость держателя проверена по дескриптору его основного окна. Между фазами держатель завершался штатно через `--exit`.

| Условия | Медиана Sleep(1), мс |
|---|---:|
| Измеритель без запроса, до запуска держателя | 15,540 |
| Измеритель с собственным Native-запросом 0,5000 мс | 1,501 |
| Измеритель с собственным Native-запросом 1,0000 мс | 1,502 |
| Измеритель с собственным запросом WinMM 1 мс | 1,501 |
| Внешний держатель Native, окно видимо | 15,543 |
| Внешний держатель Native, скрытый запуск | 15,541 |
| Внешний держатель WinMM, скрытый запуск | 15,559 |
| Измеритель после завершения держателя | 15,544 |

Проверены шесть пар JSON/CSV и освобождение запроса CLI по сигналу Ctrl+C. Компоновка release-окна проверена по захвату его собственного HWND при 120 DPI (125%). Проверка фактического запуска по входу в Windows остаётся отдельным сценарием. Fortnite работал в фоне. Для него не проводился A/B-тест: PresentMon не был найден на стенде, а воспроизводимой игровой сцены для сравнения не было.
